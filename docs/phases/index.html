Phase 1 — Auth and security

Why. A support desk holds customer messages. The first slice locks the door: who is signed in, what that role may do, and a fixed order of checks so a later feature cannot skip the queue. Roles never go backwards: Customer → Agent → Supervisor → Admin → Super Admin.

  • Login issues a 15-minute access JWT and a 7-day zenflow_refresh cookie (HttpOnly, SameSite=Lax).
  • The role on the token is not trusted. The API reads the user row again (cached 8 seconds for the same token).
  • Each role has a home screen: customer /dashboard, agent /queue, supervisor /supervisor, admin /admin/users.

            B --> C[Access JWT 15m]

Phase 2 — Tickets, routing, Help Center

Why. Without a ticket number and a team, staff cannot find work. This slice creates #ZEN-XXXX, picks a team by keyword / category / priority / fallback, stamps SLA clocks, and stores owned Help Center articles in git (not a paid crawler).

  • Create path: Zod → quota/cooldown → spam → routing → SLA dates → ticket row → notice → audit → Nova consult (if Nova is on the team).
  • Assignee: AI teammate first, else the least-busy agent on that team.
  • Help Center markdown lives in apps/backend/kb/ and is seeded.

Phase 3 — Live workspace

Why. Refreshing the page to see a reply is slow. This slice keeps one ticket open in a three-column workspace and pushes new messages over GraphQL WebSocket (graphql-ws, not Socket.io). Related Help Center hits and canned replies sit beside the thread so an agent does not hunt.

  • Subscriptions: messageAdded, ticketUpdated, ticketCreated.
  • Related articles ranked by keyword + category.
  • Suggest-reply uses category templates and a Help Center snippet.

Phase 4 — SLA sweep, CSAT, admin

Why. A desk that never warns on late work will miss promises. A clock job walks open tickets, marks warning (2 hours left) and breach, and auto-closes resolved tickets after 48 hours. When a ticket is resolved, a 7-day CSAT window (score 1–5) opens. Admins edit users, teams, routing, and SLA policy on screen — not in SQL.

  • Cron default: every 2 minutes (*/2 * * * *), skippable with DISABLE_CRON=1.
  • Admin screens: users, teams, routing, SLA, knowledge.
  • Rule-based Q&A: low score answers “I do not know” and still cites sources.

            W -->|no| B{Past due?}

            B -->|no| OK[Leave]
            R[RESOLVED 48h ago] --> AC[Auto-close]

Use case. Supervisor sees a ticket in warning before it breaches.
Use case. Customer rates 4; the score is clamped if someone posts 9.

Phase 5 — Appearance

Why. Shared “dark mode for the whole company” fights over a demo laptop. Appearance is stored per signed-in user. Login and register stay on the default light theme so a public page never inherits yesterday’s dark tokens.

  • Settings at /settings for any signed-in role.
  • Tokens: hex, contrast, font stack — validated on both UI and API.
  • Ticket list views (filters the user prefers) sit with the same user record.

Phase 6 — Analytics and consultants

Why. Supervisors need volume and CSAT without exporting a spreadsheet. Admins need a consultant board. Charts read a 30-day analytics pack; consultant lists use 90 days of assigned tickets (112 days on a profile) so the page does not scan the whole history on every tab click.

  • /analytics — Supervisor and above.
  • /admin/consultants — Admin and above.
  • Leaderboard ties break with a stable sort (localeCompare + id).

Phase 7 — Nova and owned Help Center

Why. First reply should not wait on a person if the answer is already in the Help Center. Nova is a seeded AI user. It retrieves owned markdown. If a local Ollama process is healthy it writes a grounded answer; otherwise it extracts from the articles. Below 0.45 confidence, or with zero hits, it hands the ticket to a human. Staff may save a reply as an internal unpublished draft. Admin publishes. Nothing goes public by itself.

  • Handoff threshold: 0.45 in consultMath.ts.
  • Ollama is optional. Retrieval still works if the model is down.
  • Draft body is tagged “Internal until an admin publishes.”

            K --> O{Ollama warm?}
            O -->|yes| M[Local model + sources]
            O -->|no| E[Extractive answer]
            M --> C{confidence and hits}
            E --> C
            C -->|low or 0 hits| H[Handoff to person]
            C -->|ok| R[Reply in thread]

Phase 8 — Cookie, migrations, files, bell

Why. Demo databases that were “pushed” once drifted. Refresh tokens in JSON were easy to steal from frontend storage. This slice commits Prisma migrations, puts the refresh token in an HttpOnly cookie, stores attachments on local disk (gitignored), and writes in-app notices for create / assign / reply / SLA.

  • Cookie name: zenflow_refresh. Secure flag only when NODE_ENV=production.
  • Uploads: path jail, size cap, no .. traversal.
  • Public GraphQL errors hide Prisma schema text.

Phase 9 — UI polish, speed, QA report

Why. Admin tabs felt empty while Next.js compiled each client page, then auth hit MySQL twice. This slice does not add roles. It makes the same screens paint sooner (Turbopack, skeletons, 8s identity cache, 90-day packs, in-browser list search) and publishes a phase-by-phase test sheet so coverage is visible without a terminal.

  • 140 Prisma-free unit tests, 100% c8 lines on that pack. Live e2e when GraphQL is up.
  • PWA chrome at 1024px and below. Login splash three scenes, skip if already seen or reduced motion.
  • New-ticket Help Center search still waits for 4 characters before GraphQL.
